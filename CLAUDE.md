These four principles apply to all work in this repository.

**1. Think Before Coding**
State assumptions explicitly. If uncertain, ask. Surface confusion and tradeoffs rather than making silent decisions.

**2. Simplicity First**
Minimum code that solves the problem. Nothing speculative. Avoid unrequested features, premature abstractions, or speculative error handling.

## Project Overview

This repository is a production-ready setup for deploying **Velero** on **Azure Kubernetes Service (AKS)** via **ArgoCD** (GitOps). Authentication uses **Workload Identity** (no storage keys). It includes CSI-based PVC snapshots, cost-optimised Azure storage lifecycle policies, automated backup schedules, and shell scripts for setup and E2E testing.

## Authentication: Workload Identity

This setup uses Azure AD Workload Identity — no storage account keys are created or stored.

**How it works:**
1. A User-Assigned Managed Identity is created (`velero-identity` by default).
2. Role assignments: `Storage Blob Data Contributor` on the storage account, `Disk Snapshot Contributor` + `Reader` on the resource group.
3. A federated credential links the identity to the Kubernetes service account `velero/velero` via the AKS OIDC issuer.
4. The Azure Workload Identity webhook injects a short-lived AAD token into the Velero pod at runtime.
5. The Azure Velero plugin uses `useAAD: "true"` to authenticate with this token.

**Requirements:** AKS must have OIDC issuer and Workload Identity enabled (`--enable-oidc-issuer --enable-workload-identity`). `setup-azure.sh` handles this automatically.

## Common Tasks

### Initial Setup
```bash
cp config/config.example.env config/config.env
# Fill in AZURE_SUBSCRIPTION_ID, AZURE_RESOURCE_GROUP, AZURE_LOCATION, AKS_CLUSTER_NAME
chmod +x scripts/setup-azure.sh
./scripts/setup-azure.sh          # Provisions Azure + Workload Identity + annotates SA
kubectl apply -f argocd/velero-application.yaml
```

### Verify Deployment
```bash
./scripts/verify-installation.sh  # Checks Workload Identity, BSL, CSI, schedules
kubectl get pods -n velero
kubectl get backupstoragelocation -n velero
```

### Run E2E Tests
```bash
./scripts/test-backup-restore.sh              # Full suite: namespace + cross-NS + PVC
./scripts/test-backup-restore.sh --skip-pvc  # Skip CSI snapshot test
./scripts/test-backup-restore.sh --keep-resources  # Preserve test resources after run
```

### Manual Backup / Restore
```bash
velero backup create my-backup --include-namespaces=production
velero backup get
velero restore create --from-backup my-backup
```

## E2E Test Coverage (`test-backup-restore.sh`)

| Test | What it verifies |
|------|-----------------|
| Pre-flight | Velero pod running, Workload Identity annotation, webhook present, BSL Available |
| Namespace backup & restore | Deployment, ConfigMap, Secret backed up and restored; data integrity checked |
| Cross-namespace restore | Restore into a different namespace via `--namespace-mappings` |
| PVC backup & restore | CSI snapshot of a 1Gi PVC; data written pre-backup is verified post-restore |

## Azure Cost Optimisations
- Storage: `Standard_LRS` (cheapest redundancy)
- Lifecycle: Hot → Cool (30 d) → Archive (90 d) → Delete (180 d)
- Incremental managed-disk snapshots only
- Node agent disabled (`deployNodeAgent: false`)
- Estimated: ~$7–12/month for a 100 GB cluster

## Security Posture
- No storage keys created or stored — Workload Identity only
- Velero pods: non-root (`runAsUser: 65534`), all capabilities dropped, read-only root FS
- Storage account: HTTPS-only, TLS 1.2 minimum, public blob access disabled
- RBAC scoped to minimum required roles

## Prerequisites
- `az` CLI authenticated to the correct subscription
- `kubectl` configured against the target AKS cluster
- `helm` 3.x installed
- ArgoCD installed in the cluster
- Azure RBAC on your principal: ability to create identities, assign roles, and manage storage in the resource group
